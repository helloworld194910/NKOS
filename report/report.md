1. **理解最小可执行内核与启动流程。** 掌握一台 RISC-V 计算机从加电复位到操作系统内核接管控制权的完整接力过程：复位引导代码（`0x1000`）→ 固件 OpenSBI（`0x80000000`）→ 内核入口（`0x80200000`），理解"固件 → 引导程序 → 操作系统"这三级跳各自的职责与衔接方式。

3. **掌握用 OpenSBI 加载内核、用 QEMU 模拟运行。** 理解 OpenSBI 作为 bootloader 如何把内核镜像加载到 `0x80200000` 并把控制权交给内核，以及 `make qemu` 背后"编译 → 链接 → 生成镜像 → QEMU 加载"的完整构建链路。

4. **理解从 SBI 到 stdio 的输出功能构建。** 明白在没有宿主操作系统标准库的情况下，如何从 OpenSBI 提供的最底层 `ecall` 接口出发，逐层封装出功能等同标准库 `printf` 的 `cprintf`，为后续实验的调试手段打下基础。

## 三、实验整体逻辑分析

### 2.1 本章节的逻辑主线

[请用自己的话描述本章实验的核心主线，例如：
- 本章围绕哪个核心主题展开？（例如：用户进程管理、虚拟内存、文件系统等）
- 整个实验解决什么问题？（例如：如何让用户程序运行在操作系统之上）]
本章围绕一个核心问题展开：**如何让一段我们自己写的 C 代码，在"没有操作系统"的裸机环境下跑起来，并在屏幕上输出一行文字？** 这个问题看似简单，但在普通程序里由操作系统和标准库默默代劳的所有工作——加载、内存布局、栈、输出——在这里都必须由我们自己一步步补上。

据此，整个实验的逻辑线可以概括为一条"自底向上、环环相扣"的链条：

**搭环境（能编译）→ 定布局（能落到正确的地址）→ 走构建（能生成镜像）→ 走启动（能被执行）→ 造输出（能说话）。**

五个环节缺一不可，任何一环断掉，最终那行 `(THU.CST) os is loading ...` 都出不来：

- **搭环境**：宿主机是 x86，目标机是 RISC-V，所以需要交叉编译工具链；没有真实硬件，所以用 QEMU 模拟一台 64 位 RISC-V 机器。
- **定布局**：内核必须被加载到固定物理地址 `0x80200000` 才与 OpenSBI 的交接约定对上，这由链接脚本 `tools/kernel.ld` 描述——它决定了内核各段在内存中的位置以及入口符号 `kern_entry`。
- **走构建**：Makefile 把"编译所有源文件 → 链接成 ELF → `objcopy` 转成二进制镜像"这一串命令固化下来，一条 `make qemu` 就能完成构建并直接启动。
- **走启动**：QEMU 加电后 PC 先指向 `0x1000` 的复位代码，随后进入 OpenSBI（`0x80000000`），再由 OpenSBI 把控制权交到 `0x80200000` 的 `kern_entry`，最后进入 C 语言编写的 `kern_init`。
- **造输出**：内核自身没有任何标准库可依赖，只能抓住 OpenSBI 暴露的 `ecall` 接口，自底向上封装出 `cprintf`，把字符送到屏幕上。
### 2.2 功能的逐步实现

[说明本章实验是按照什么顺序逐步实现各个功能的，以及为什么要按这个顺序，例如：

1. 首先实现**功能A** → 为什么首先实现这个？（例如：建立系统调用接口是后续所有用户态功能的基础）
2. 接着再完善**功能B** → 为什么接着实现这个？（例如：有了系统调用后，需要能够加载和启动第一个用户进程）
3. 然后完成**功能C** → 为什么然后实现这个？（例如：有了第一个进程后，需要实现进程复制功能）
4. 最后补充了**功能D** → 为什么最后实现这个？（例如：最后完善进程退出和清理机制，形成完整闭环）]
本章没有新增功能意义上的代码编写（各练习都是理解性的阅读与验证），所谓逐步实现，指的是实验代码从无到有地打通整条启动 + 输出链路的过程。按构建与运行的先后顺序梳理如下：

1. **搭建实验环境：WSL + 交叉编译器 + QEMU。** 这是所有后续工作的前提。在 WSL 中安装 `riscv64-unknown-elf-*` 工具链（编译器 `gcc`、链接器 `ld`、目标文件处理工具 `objcopy`/`objdump`）与 `qemu-system-riscv64`，使宿主机同时具备"为 RISC-V 目标编译"与"模拟 RISC-V 机器运行"两种能力。

2. **划分项目结构：明确各目录职责。** 代码按层次组织，构建脚本靠目录约定把它们收拢起来：

   | 目录/文件 | 作用 |
   |---|---|
   | `kern/init/` | 内核入口与初始化：`entry.S` 是汇编入口，`init.c` 里的 `kern_init` 是 C 主函数 |
   | `kern/driver/` | 设备驱动封装：`console.c` 把单个字符输出封装成 `cons_putc` |
   | `kern/libs/` | 内核侧工具：`stdio.c` 实现 `cprintf`/`cputs` 等格式化输出 |
   | `libs/` | 与内核无关的通用库：`sbi.c` 封装 SBI 调用、`printfmt.c` 做格式化解析、`string.c` 提供 `memset` 等、`defs.h` 定义基础类型与宏 |
   | `kern/mm/` | 内存相关头文件：`memlayout.h`、`mmu.h` 定义栈大小、页大小等常量 |
   | `tools/` | 构建辅助：`kernel.ld` 链接脚本、`function.mk` 定义 Makefile 宏 |
   | `Makefile` | 顶层构建脚本，组织整个编译、链接、镜像生成与运行流程 |

3. **描述内存布局：用链接脚本把内核钉在 `0x80200000`。** `tools/kernel.ld` 用 `BASE_ADDRESS = 0x80200000` 加 `. = BASE_ADDRESS` 固定内核起始地址，按 `.text → .rodata → .data → .bss` 的顺序排布各段，并用 `ENTRY(kern_entry)` 指定入口符号；`entry.S` 中预留的内核栈空间（`bootstack`/`bootstacktop`）也据此得到确定地址。

4. **编译与生成镜像：Makefile 固化构建流程。** `make` 通过 `tools/function.mk` 中定义的宏，为 `libs/` 与 `kern/` 下每个 `.c`/`.S` 源文件生成编译规则（产出 `obj/` 下的 `.o`），再用 `ld -T tools/kernel.ld` 链接成 ELF 文件 `bin/kernel`，最后用 `objcopy --strip-all -O binary` 去掉符号与调试信息、生成纯二进制镜像 `bin/ucore.img`。

5. **内核启动执行：从入口汇编到 C 主函数。** `make qemu` 以 `-bios default` 提供 OpenSBI 固件、以 `-device loader,file=bin/ucore.img,addr=0x80200000` 把内核镜像放到指定地址。QEMU 加电后 PC 从 `0x1000` 的复位代码开始，进入 OpenSBI（`0x80000000`），OpenSBI 完成初始化后跳到 `0x80200000` 的 `kern_entry`；`entry.S` 先设置栈指针 `sp`，再 `tail kern_init` 移交控制权；`kern_init` 清零 `.bss` 段、调用 `cprintf` 输出一行信息后进入死循环。

6. **格式化输出：从 SBI 到 stdio 自底向上封装。** 内核运行在 S 模式，既无法直接操作硬件，也拿不到标准库，只能借助 OpenSBI 提供的 `ecall` 接口：`libs/sbi.c` 的 `sbi_call` 用内联汇编把功能号 `SBI_CONSOLE_PUTCHAR` 放入 `a7`、字符放入 `a0` 后执行 `ecall`，封装出 `sbi_console_putchar`；再经 `kern/driver/console.c` 的 `cons_putc`、`kern/libs/stdio.c` 的 `cputch` 逐层封装，最终得到功能等同 `printf` 的 `cprintf`。

以上六个环节串起来，就打通了从一段 C 代码到屏幕上的一行字的完整通路。本章构建的只是一个最小骨架，后续实验正是在它之上，把中断处理、内存管理、进程调度等逐步安回去。

### 功能模块：内核入口点与内存布局

**负责人：** 2412790-杨茜茹

#### 模块功能描述

`entry.S` 里的指令能正确工作，前提是它们被安排在了正确的地址上——这件事不是 `entry.S` 自己决定的，而是 `tools/kernel.ld` 划定的。练习 1 已经验证了具体指令层面的地址计算，这里要回答另一个问题：链接脚本凭什么能保证这些地址是对的、安排成这样有什么道理。

`BASE_ADDRESS = 0x80200000` 加 `. = BASE_ADDRESS`，把整个内核的起始地址钉死在这里。我没有把这当成一个"约定俗成"就接受，而是去确认了这个约定不成立会怎样：C/汇编代码里对变量、函数的访存指令，在链接完成时就已经把具体地址写进了机器码编码本身——练习1 里验证过的 `auipc sp,0x3`，这个 `0x3` 就是根据 `BASE_ADDRESS` 在编译期算死的。如果实际加载地址和这个约定不一致，这类写死的地址全部失效，代码从第一条指令起就是错的，这不是"可能出问题"，而是必然出问题。`ENTRY(kern_entry)` 加上排在 `.text` 段最前面的 `*(.text.kern_entry)` 匹配规则，两者合起来保证了 OpenSBI 跳到 `0x80200000` 时，落地的第一条指令必须是 `kern_entry`，不存在"大概率是"这种模糊地带。

**逐行读脚本时注意到的一处细节**：`. = ALIGN(0x1000)` 只出现在 `.rodata` 和 `.data` 之间，`.text` 和 `.rodata` 之间没有，`.bss` 前面也没有单独对齐。我的判断是，这不是随手安排的——`.text`（代码）和 `.rodata`（只读常量）都不需要写权限，可以共享同一批内存页；但 `.data`（可读写全局变量）一旦将来引入内存保护机制，就必须从页边界开始独占空间，否则没法只对这一页开放写权限。`.bss` 紧跟 `.data` 且不再单独对齐，同样符合"可读写内容划进同一组权限管理"这个逻辑。但我没有把这个判断写成确定结论——lab1 本身还没有实现分页机制，这个推测目前缺乏运行时证据支撑，只能算是读脚本结构得出的合理猜测，留待后续涉及虚拟内存的实验去验证，不采信为既定事实。

链接脚本与 `init.c` 之间还有一处容易被忽略的直接耦合：`PROVIDE(edata = .)`、`PROVIDE(end = .)` 定义的符号，被 `kern_init` 直接用来计算 `.bss` 段范围并清零。这意味着链接脚本不只是给汇编代码看的"地图"，C 代码同样要靠它提供的符号才能正确初始化——如果有人改了链接脚本里段的排列顺序或漏掉某个 `PROVIDE`，最先暴露问题的很可能不是链接报错，而是运行时 `.bss` 没清零、全局变量里是垃圾值，这种故障远比链接失败更隐蔽、更难定位。

#### 小结

`kernel.ld` 不是一份静态的内存布局说明，它定义的地址约定和符号被 `entry.S`（建立栈）和 `init.c`（清零 `.bss`）两处代码分别、真实地消费着。这也是为什么修改链接脚本这类"看起来只是配置"的文件，必须对整条启动链路的影响有清楚认识，不能当成孤立参数去改。

#### AI 辅助阅读与人工核对

entry.S 和链接脚本的内容，是我先自己通读一遍，再带着具体疑问和 AI 逐句核对的：比如为什么栈要设在预留空间的"顶端"而不是起始处、`la` 这类伪指令展开后的真实指令是什么。AI 讲解之后，我没有直接采信，而是要求用真实编译数据验证——在 WSL 中执行 `make`，用 `grep` 查看编译生成的 `obj/kernel.sym` 和 `obj/kernel.asm`，把 `bootstack`、`bootstacktop` 的真实地址和 `la sp, bootstacktop` 展开后的具体指令发回去核对，确认地址计算（`0x80200000 + 0x3000 = 0x80203000`）与符号表结果一致，这部分内容写进了练习1。

### 功能模块：从 `cprintf` 到 SBI 控制台输出

**负责人：** 2413921-程子涵

#### 模块功能描述

本实验还没有可供内核调用的宿主操作系统标准库，因此格式化输出由实验代码自行实现。`kern/init/init.c` 中的 `kern_init` 调用 `cprintf`；`kern/libs/stdio.c` 中的 `cprintf` 和 `vcprintf` 把格式串及参数交给 `libs/printfmt.c` 的 `vprintfmt` 解析。每产生一个字符，回调 `cputch` 依次调用 `cons_putc`（`kern/driver/console.c`）和 `sbi_console_putchar`（`libs/sbi.c`）。最终 `sbi_call` 把功能号 `SBI_CONSOLE_PUTCHAR = 1` 放入 `a7/x17`，字符放入 `a0/x10`，执行 `ecall`，由 OpenSBI 提供控制台服务。链路可概括为：

```text
kern_init → cprintf → vcprintf → vprintfmt → cputch
          → cons_putc → sbi_console_putchar → sbi_call → ecall → OpenSBI 控制台
```

这里的 `ecall` 是 S 模式内核向更高特权级固件请求服务；与以后用户程序向内核发起的系统调用使用同一类陷入机制，但请求方、服务方和调用约定不同。截图中的 `(THU.CST) os is loading ...` 是该链路产生的实际输出。

我先沿 `kern_init` 的调用点逐层查找函数定义，自己整理上述输出链路，再用 AI 辅助解释 `vprintfmt` 的字符回调和 SBI 寄存器约定。对 AI 给出的说法，我回到 `kern/libs/stdio.c`、`kern/driver/console.c` 和 `libs/sbi.c` 核对调用关系与寄存器赋值，并用启动输出截图确认实际现象。本部分没有让 AI 生成或修改内核代码，也没有进行“生成代码后多轮修复”的迭代；对应的阅读辅助提示词整理在 [prompt.md](./prompt.md) 中。

### 练习 1：理解内核启动中的程序入口操作

**负责人：** 2412790-杨茜茹

**问题：** 阅读 `kern/init/entry.S` 内容代码，结合操作系统内核启动流程，说明指令 `la sp, bootstacktop` 完成了什么操作，目的是什么？`tail kern_init` 完成了什么操作，目的是什么？

**分析：**

OpenSBI 把控制权交到 `0x80200000` 时，除了 PC 指向这里，没有为接下来的代码准备任何执行环境，尤其没有栈。而紧接着要执行的 `kern_init` 是 C 函数，任何一次函数调用都要用到栈。`entry.S` 只有两条真正执行的指令，拆开看，这两条指令恰好分别对应"搭建执行环境"和"移交控制权"这两件必须做、且只能做一次的事。

**`la sp, bootstacktop`：** 这是一条伪指令，表面上看是"把地址装进寄存器"，但我没有停留在这个字面解释上，而是去查了它展开后的真实指令（`obj/kernel.asm`）：

```asm
80200000: auipc sp,0x3
80200004: mv sp,sp
```

确实被拆成了两条。这里我排除了"随便哪种方式都行"这种想法——RISC-V 指令编码定长 32 位，一条指令根本装不下一个完整的目标地址，所以必须靠 `auipc`（以当前 PC 为基准、加一个高位偏移）先拼出一个大致地址，这不是编译器"多此一举"，而是指令集本身的硬性限制决定的。我用符号表（`obj/kernel.sym`）核对了这个偏移量算出来的结果：`bootstack = 0x80201000`，`bootstacktop = 0x80203000`，`0x80200000 + 0x3000` 正好等于 `0x80203000`，验证了这条"PC 相对寻址"确实精确落在目标地址上，不是凑巧。

栈指针设在 `bootstacktop`（区间顶端）而不是 `bootstack`（起点），我一开始以为是随意的命名习惯，后来确认这是和 RISC-V 栈"从高地址向低地址增长"这个架构约定强绑定的——如果设在起点，第一次压栈就会立刻写出预留空间之外，这不是风格问题，是会直接导致错误的设计约束。这块空间大小是 `KSTACKPAGE(2) × PGSIZE(4096) = 8192` 字节，符号表里 `0x80203000 - 0x80201000 = 0x2000` 也印证了这一点。至于为什么具体选了 2 页而不是 1 页或更多，`entry.S` 和 `memlayout.h` 本身没有给出直接依据，我没有采信"随便取个经验值"这类缺乏支撑的说法，这里如实标注为待后续实验验证的开放问题，而不是强行给出一个解释。

**`tail kern_init`：** 跳转到 `kern_init`，且不保存返回地址。我验证了一个假设：如果把这条指令换成普通的 `call kern_init`，单从运行结果看，会不会出错？结论是不会——因为 `kern_init` 本身进入死循环、永不返回，`ra` 寄存器里存不存东西根本不会被用到。但这恰恰说明 `tail` 的价值不在于"不用就会错"，而在于它用指令本身准确表达了"这是终点，不是中转站"这个设计意图，同时省掉了一次多余的寄存器写入。这个判断和 `kern_init` 在 `init.c` 中被标注 `__attribute__((noreturn))` 是互相印证的——一处用汇编指令的选择、一处用 C 语言的函数属性，各自独立地表达了同一个事实。

**问题回答：** `la sp, bootstacktop` 通过 `auipc` 与偏移拼接出预留栈空间顶端的地址（`0x80203000`）并装入 `sp`，目的是在进入 C 代码前建立可用的函数调用环境，这一实现方式本身是 RISC-V 定长指令编码限制下的必然结果，不是设计者的任意选择。`tail kern_init` 以不保存返回地址的方式跳转到 `kern_init`，目的是把控制权永久移交给内核初始化逻辑；经过对比验证，换成普通调用不会导致功能错误，但 `tail` 更准确地表达了"内核启动是单向流程"这一设计意图，这是语义层面而非正确性层面的选择。

### 练习 2：使用 GDB 验证启动流程

**负责人：** 2413921-程子涵

**问题：** RISC-V 硬件加电后最初执行的几条指令位于什么地址？它们主要完成哪些功能？

**调试过程与观察：**

1. 在 WSL 的实验目录执行 `make debug`。本项目的 Makefile 用 `-s -S` 启动 QEMU：开放本地 GDB 端口并让虚拟 CPU 在启动时暂停。另一终端执行 `make gdb`，加载 `bin/kernel` 的调试符号，按 RV64 架构连接 `localhost:1234`。连接后 GDB 显示当前 PC 为 `0x1000`。
2. 执行 `p/x $pc` 和 `x/8i $pc` 查看复位处指令，再用 `si` 单步。截图中 PC 从 `0x1000` 依次到 `0x1004`、`0x1008`，与反汇编地址相符。
3. 参考指导书提示，对 `0x80200000` 设置硬件写监视点；随后未设置内核入口的执行断点，就直接执行 `c`。GDB 一直显示 `Continuing.`，没有停在预期位置。此次尝试未取得监视点命中的记录，因而终止调试进程并重新启动。
4. 重新从起点对 `0x80200000` 设置执行断点并继续运行。GDB 在 `kern_entry` 的 `kern/init/entry.S:7` 停下，`p/x $pc` 显示 `0x80200000`。此时反汇编显示先设置 `sp`，随后跳转到 `kern_init`。进一步单步后 `sp` 从进入内核时的 `0x8001bd80` 变为 `0x80203000`，证实内核切换到自己的启动栈。

**调试中遇到的问题与处理：** 写监视点关注的是目标地址发生写入，并不会因为 CPU 执行到 `0x80200000` 就停下。本项目的 Makefile 使用 QEMU `-device loader` 把内核镜像放到该地址；截图无法证明这一步是否会触发 GDB 所设的 CPU 写监视点。第一次尝试只设监视点就继续运行，未出现可观察的监视点命中，程序也没有自动暂停；`kern_init` 输出后会进入死循环。终止该次调试并重启后，改用 `b *0x80200000` 在内核第一条指令处设置执行断点，成功观察到 `kern_entry`。这次问题说明应根据要验证的事件选择断点类型，并在执行 `c` 前设置好能够捕获目标事件的断点。

## 六、实验总结与收获

### 对操作系统的理解

**程子涵：本实验知识点与 OS 原理的对应关系**

| 本实验中的知识点 | 对应的 OS 原理及关系、差异 |
|---|---|
| 从 `0x1000` 到 `0x80200000` 的启动交接 | 对应操作系统的引导过程。CPU 先执行复位引导代码，再进入固件，最后进入内核。实验用 QEMU 和 OpenSBI 展示了接力关系；真实机器还会有平台相关初始化、引导加载器和更多检查。 |
| 内核入口与独立启动栈 | 对应内核执行上下文和栈管理。`kern_entry` 设置 `sp` 后才进入 C 函数，说明内核运行不能继续依赖固件先前的栈。本实验只有一条简单执行路径，尚未涉及每个进程或每个 CPU 的内核栈。 |
| `cprintf` 经 SBI 输出 | 对应分层 I/O 与硬件抽象。格式化层负责把数据转成字符，控制台层负责逐字符输出，SBI 层屏蔽底层设备差异。本实验借用固件服务，并没有实现完整的设备驱动、缓冲或文件描述符。 |
| S 模式执行 `ecall` | 对应特权级切换与陷入机制。内核通过 `ecall` 请求 M 模式 SBI 服务；原理课中的用户态系统调用通常是 U 模式陷入 S 模式。机制相似，但调用方向与服务对象不同。 |
| GDB 观察 PC、指令和寄存器 | 对应处理器状态与控制流分析。`pc` 表示下一条指令地址，`sp` 表示当前栈顶；断点和单步让引导过程可验证。GDB 是实验调试手段，本身不是内核提供的运行时功能。 |

**原理课中重要、但 Lab 1 尚未实现的内容：**

1. **进程与线程调度：** 尚无进程控制块、上下文切换或调度算法；`kern_init` 输出后进入死循环。
2. **虚拟内存管理：** 尚无页表、地址空间隔离、缺页处理和页面置换；本实验主要观察链接与加载地址。
3. **中断和异常处理：** 虽通过 `ecall` 使用 SBI 服务，但没有实现完整的内核 trap 处理、外设中断分发及异常恢复。
4. **文件系统与持久化：** 控制台输出不等于文件 I/O，本实验没有目录、文件、缓存或磁盘管理。
5. **同步与并发：** 尚无锁、信号量及多任务竞争场景，也未讨论死锁处理。

#### 小组整体理解

这次实验让我们从一个最小可执行内核出发，把"一段 C 代码如何变成屏幕上的一行字"完整地走了一遍，也体会到：写一个裸机内核，意味着把平时在 Linux 上被工具链"默认"掉的环节——目标架构、链接脚本、标准库、加载地址——都显式地补回来。交叉编译对应原理课中"源代码如何变成目标平台可执行代码"（编译、汇编、链接）；用链接脚本把内核钉在 `0x80200000` 对应"程序内存布局与地址相关性"；`make qemu` 的"编译 → 链接 → 镜像 → 加载"四步，则把抽象的构建系统与可执行文件格式（ELF 与 bin 的区别）落到了真实命令上。把整章串成"搭环境 → 定布局 → 走构建 → 走启动 → 造输出"一条链，我们才真正理解：操作系统之所以是"裸机之上的第一层软件"，正是因为它要亲手接过这些底层工作。

在入口点与内存布局上，印象最深的是汇编入口与链接脚本互相咬合：`entry.S` 里的 `la sp, bootstacktop` 之所以正确，是因为链接脚本把内核钉在 `0x80200000` 并给 `bootstack`/`bootstacktop` 定了地址；而 `kern_init` 清零 `.bss` 靠的又是链接脚本 `PROVIDE(edata/end)` 导出的符号。内核是地址相关代码，编译链接时就把绝对地址写进了指令，所以必须加载到编译时假设的位置；栈"从高地址向低地址增长"这一架构约定，也直接决定了 `sp` 必须指向预留空间的顶端而非起点。

在启动流程与输出上，我们梳理了"复位引导代码（`0x1000`）→ 固件 OpenSBI（`0x80000000`）→ 内核入口（`0x80200000`）"的三级跳，以及内核借 `ecall` 请求 M 模式 SBI 服务、自底向上封装出 `cprintf` 的输出链路。据此，本实验知识点与 OS 原理可以这样对应：启动交接对应引导过程；内核入口与独立启动栈对应内核执行上下文与栈管理；`cprintf` 经 SBI 输出对应分层 I/O 与硬件抽象；S 模式 `ecall` 对应特权级切换与陷入机制（与用户态系统调用同类机制、但方向是 S→M 而非 U→S）；GDB 观察 PC/寄存器则对应处理器状态与控制流分析。反过来，原理课中重要的进程调度、虚拟内存、完整的中断异常处理、文件系统与同步并发，本实验都尚未触及——`kern_init` 输出后便进入死循环。
