## 一、实验目的

本实验是 ucore 系列实验的起点，目标是构建一个"比麻雀更小的麻雀"——一个最小可执行内核，并完整理解它从"被编译出来"到"在屏幕上打印一行文字"的全过程。具体而言，本次实验要达到以下目的：

1. **理解最小可执行内核与启动流程。** 掌握一台 RISC-V 计算机从加电复位到操作系统内核接管控制权的完整接力过程：复位引导代码（`0x1000`）→ 固件 OpenSBI（`0x80000000`）→ 内核入口（`0x80200000`），理解"固件 → 引导程序 → 操作系统"这三级跳各自的职责与衔接方式。

2. **掌握用链接脚本描述内存布局，并完成交叉编译。** 理解 `.text`/`.rodata`/`.data`/`.bss` 等段的含义与排布，学会用链接脚本（`tools/kernel.ld`）把内核放在固定物理地址 `0x80200000` 开始的位置；掌握在 x86 宿主机上使用 `riscv64-unknown-elf-*` 交叉工具链编译、链接出 RISC-V 可执行文件，再用 `objcopy` 生成纯二进制内核镜像。

3. **掌握内核镜像的加载与 QEMU 模拟运行。** 理解内核镜像被放置到 `0x80200000`、再由 OpenSBI 把控制权交给内核的交接方式（本项目中镜像由 QEMU 的 `-device loader` 放入物理内存，详见练习 2），以及 `make qemu` 背后"编译 → 链接 → 生成镜像 → QEMU 加载"的完整构建链路。

4. **理解从 SBI 到 stdio 的输出功能构建。** 明白在没有宿主操作系统标准库的情况下，如何从 OpenSBI 提供的最底层 `ecall` 接口出发，逐层封装出功能等同标准库 `printf` 的 `cprintf`，为后续实验的调试手段打下基础。

5. **借助 AI 辅助阅读与分析。** 学会用 AI 工具辅助阅读实验文档与源码、梳理整体逻辑线，同时坚持用真实编译产物和运行结果对 AI 的解释逐项人工核对，做到借助而不盲从。

## 三、实验整体逻辑分析

### 3.1 本章节的逻辑主线

本章围绕一个核心问题展开：**如何让一段我们自己写的 C 代码，在"没有操作系统"的裸机环境下跑起来，并在屏幕上输出一行文字？** 这个问题看似简单，但在普通程序里由操作系统和标准库默默代劳的所有工作——加载、内存布局、栈、输出——在这里都必须由我们自己一步步补上。

据此，整个实验的逻辑线可以概括为一条"自底向上、环环相扣"的链条：

**搭环境（能编译）→ 定布局（能落到正确的地址）→ 走构建（能生成镜像）→ 走启动（能被执行）→ 造输出（能说话）。**

五个环节缺一不可，任何一环断掉，最终那行 `(THU.CST) os is loading ...` 都出不来：

- **搭环境**：宿主机是 x86，目标机是 RISC-V，所以需要交叉编译工具链；没有真实硬件，所以用 QEMU 模拟一台 64 位 RISC-V 机器。
- **定布局**：OpenSBI 完成初始化后会跳转到固定地址 `0x80200000`，因此内核镜像的第一条指令必须位于该地址。这由链接脚本 `tools/kernel.ld` 描述——它决定了内核各段在内存中的位置以及入口符号 `kern_entry`。
- **走构建**：Makefile 把"编译所有源文件 → 链接成 ELF → `objcopy` 转成二进制镜像"这一串命令固化下来，一条 `make qemu` 就能完成构建并直接启动。
- **走启动**：QEMU 加电后 PC 先指向 `0x1000` 的复位代码，随后进入 OpenSBI（`0x80000000`），再由 OpenSBI 把控制权交到 `0x80200000` 的 `kern_entry`，最后进入 C 语言编写的 `kern_init`。
- **造输出**：内核自身没有任何标准库可依赖，只能抓住 OpenSBI 暴露的 `ecall` 接口，自底向上封装出 `cprintf`，把字符送到屏幕上。

### 3.2 功能的逐步实现

本章没有新增功能意义上的代码编写（各练习都是理解性的阅读与验证），所谓逐步实现，指的是实验代码从无到有地打通整条启动 + 输出链路的过程。按构建与运行的先后顺序梳理如下：

1. **搭建实验环境：WSL + 交叉编译器 + QEMU。** 这是所有后续工作的前提。在 WSL 中安装 `riscv64-unknown-elf-*` 工具链（编译器 `gcc`、链接器 `ld`、目标文件处理工具 `objcopy`/`objdump`）与 `qemu-system-riscv64`，使宿主机同时具备"为 RISC-V 目标编译"与"模拟 RISC-V 机器运行"两种能力。

2. **划分项目结构：明确各目录职责。** 代码按层次组织，构建脚本靠目录约定把它们收拢起来：

   | 目录/文件 | 作用 |
   |---|---|
   | `kern/init/` | 内核入口与初始化：`entry.S` 是汇编入口，`init.c` 里的 `kern_init` 是 C 主函数 |
   | `kern/driver/` | 设备驱动封装：`console.c` 把单个字符输出封装成 `cons_putc` |
   | `kern/libs/` | 内核侧工具：`stdio.c` 实现 `cprintf`/`cputs` 等格式化输出 |
   | `libs/` | 与内核无关的通用库：`sbi.c` 封装 SBI 调用、`printfmt.c` 做格式化解析、`string.c` 提供 `memset` 等、`defs.h` 定义基础类型与宏 |
   | `kern/mm/` | 内存相关头文件：`memlayout.h`、`mmu.h` 定义栈大小、页大小等常量 |
   | `tools/` | 构建辅助：`kernel.ld` 链接脚本、`function.mk` 定义 Makefile 宏 |
   | `Makefile` | 顶层构建脚本，组织整个编译、链接、镜像生成与运行流程 |

3. **描述内存布局：用链接脚本把内核放在 `0x80200000`。** `tools/kernel.ld` 用 `BASE_ADDRESS = 0x80200000` 加 `. = BASE_ADDRESS` 固定内核起始地址，按 `.text → .rodata → .data → .bss` 的顺序排布各段，并用 `ENTRY(kern_entry)` 指定入口符号；`entry.S` 中预留的内核栈空间（`bootstack`/`bootstacktop`）也据此得到确定地址。

4. **编译与生成镜像：Makefile 固化构建流程。** `make` 通过 `tools/function.mk` 中定义的宏，为 `libs/` 与 `kern/` 下每个 `.c`/`.S` 源文件生成编译规则（产出 `obj/` 下的 `.o`），再用 `ld -T tools/kernel.ld` 链接成 ELF 文件 `bin/kernel`，最后用 `objcopy --strip-all -O binary` 去掉符号与调试信息、生成纯二进制镜像 `bin/ucore.img`。

5. **内核启动执行：从入口汇编到 C 主函数。** `make qemu` 以 `-bios default` 提供 OpenSBI 固件、以 `-device loader,file=bin/ucore.img,addr=0x80200000` 把内核镜像放到指定地址。QEMU 加电后 PC 从 `0x1000` 的复位代码开始，进入 OpenSBI（`0x80000000`），OpenSBI 完成初始化后跳到 `0x80200000` 的 `kern_entry`；`entry.S` 先设置栈指针 `sp`，再 `tail kern_init` 移交控制权；`kern_init` 清零 `.bss` 段、调用 `cprintf` 输出一行信息后进入死循环。

6. **格式化输出：从 SBI 到 stdio 自底向上封装。** 内核运行在 S 模式，既无法直接操作硬件，也拿不到标准库，只能借助 OpenSBI 提供的 `ecall` 接口：`libs/sbi.c` 的 `sbi_call` 用内联汇编把功能号 `SBI_CONSOLE_PUTCHAR` 放入 `a7`、字符放入 `a0` 后执行 `ecall`，封装出 `sbi_console_putchar`；再经 `kern/driver/console.c` 的 `cons_putc`、`kern/libs/stdio.c` 的 `cputch` 逐层封装，最终得到功能等同 `printf` 的 `cprintf`。

以上六个环节串起来，就打通了从一段 C 代码到屏幕上的一行字的完整通路。本章构建的只是一个最小骨架，后续实验正是在它之上，把中断处理、内存管理、进程调度等逐步安回去。

## 四、实验内容与实现

### 练习 1：理解内核启动中的程序入口操作

**负责人：** 2412790-杨茜茹

**问题：** 阅读 `kern/init/entry.S` 内容代码，结合操作系统内核启动流程，说明指令 `la sp, bootstacktop` 完成了什么操作，目的是什么？`tail kern_init` 完成了什么操作，目的是什么？

**分析：**

OpenSBI 把控制权交到 `0x80200000` 时，PC 已指向内核入口，但 `sp` 并不属于内核：练习 2 的调试中，刚进入 `kern_entry` 时 `sp = 0x8001bd80`，这是 OpenSBI 固件自己的栈空间（位于固件所在的 `0x80000000` 附近区域），既不是内核预留的，也不应被内核继续使用。而紧接着要执行的 `kern_init` 是 C 函数，任何一次函数调用都要用到栈。`entry.S` 只有两条汇编语句，恰好分别对应"建立内核自己的执行环境"和"移交控制权"这两件必须做、且只做一次的事。

**`la sp, bootstacktop`：** 这是一条伪指令，表面上看是"把地址装进寄存器"，但我没有停留在这个字面解释上，而是去查了它展开后的真实指令（`obj/kernel.asm`）：

```asm
80200000: auipc sp,0x3
80200004: mv sp,sp
```

即被拆成了两条机器指令。这是因为 RISC-V 指令定长 32 位，一条指令装不下 64 位的完整地址；在 `-mcmodel=medany` 的编译选项下，`la` 采用 PC 相对寻址：`auipc` 把当前 PC 加上一个高 20 位的偏移，再由第二条指令补上低 12 位偏移。这里低 12 位偏移恰好为 0，所以第二条指令（反汇编显示为 `mv sp,sp`，即 `addi sp,sp,0`）实际上不改变 `sp` 的值。

我用符号表（`obj/kernel.sym`）核对了这个结果：`bootstack = 0x80201000`，`bootstacktop = 0x80203000`；`auipc sp,0x3` 在 PC = `0x80200000` 处执行，得到 `0x80200000 + 0x3000 = 0x80203000`，正好等于 `bootstacktop`。

<!-- TODO(杨茜茹)：在此处插入 `grep -A2 "bootstack" obj/kernel.sym` 与 `grep -B2 -A8 "kern_entry>:" obj/kernel.asm` 的终端截图，作为本练习的核心证据。 -->

栈指针设在 `bootstacktop`（区间顶端）而不是 `bootstack`（起点），是因为栈按 RISC-V 调用约定（ABI）向低地址增长：入栈时先减小 `sp` 再写数据。若把 `sp` 设为 `bootstack`，第一次入栈就会写到预留栈空间之下，而紧挨其下的正是内核镜像前部（从 `0x80200000` 起）的代码和只读数据，会直接破坏内核自身。这块空间大小是 `KSTACKPAGE(2) × PGSIZE(4096) = 8192` 字节，符号表里 `0x80203000 - 0x80201000 = 0x2000` 也印证了这一点。至于为什么具体选了 2 页而不是 1 页或更多，`entry.S` 和 `memlayout.h` 本身没有给出依据，这里不做臆断，如实标注为待后续实验验证的开放问题。

另外，栈是在 `.data` 段中用 `.space` 预留的，所以这 8 KB 也包含在内核镜像里（`objcopy -O binary` 生成的 `.bin` 会按段布局原样展开）。

**`tail kern_init`：** 跳转到 `kern_init`，且不把返回地址保存到 `ra`。`tail` 是伪指令，按 RISC-V 约定通常展开为借助临时寄存器 `t1` 的 `auipc` + `jr`（具体以 `obj/kernel.asm` 的实际输出为准）<!-- TODO(杨茜茹)：对照 kernel.asm 确认 tail 的真实展开并改成实际指令 -->。

我思考了一个假设：如果换成普通的 `call kern_init`，会不会出错？按推理，不会：`call` 会把返回地址写入 `ra`，但 `kern_init` 永不返回，`ra` 不会被使用，所以功能上等价（这是推理，本组没有实际构建 `call` 版本做对比）。两者的差别在语义层面：`tail` 不会覆盖 `ra`、不留下返回点，准确表达了"这是终点，不是中转站"；这与 `kern_init` 在 `init.c` 中被标注 `__attribute__((noreturn))` 是互相印证的——一处用汇编指令的选择、一处用 C 语言的函数属性，表达的是同一个事实。

**问题回答：** `la sp, bootstacktop` 通过 PC 相对寻址（`auipc` 加偏移）把预留栈空间顶端的地址 `0x80203000` 装入 `sp`，目的是在进入 C 代码前把栈切换到内核自己的启动栈（此前 `sp` 指向 OpenSBI 的栈 `0x8001bd80`），建立可用的函数调用环境；拆成两条机器指令是 RISC-V 定长指令编码的结果。`tail kern_init` 以不保存返回地址的方式跳转到 `kern_init`，目的是把控制权单向移交给内核初始化函数；换成 `call` 在功能上推断不会出错，但 `tail` 更准确地表达了"启动是单向流程"。

### 功能模块：内核入口点与内存布局

**负责人：** 2412790-杨茜茹

#### 模块功能描述

`entry.S` 里的指令能正确工作，前提是内核镜像被放在了约定的地址上——这件事不是 `entry.S` 自己决定的，而是 `tools/kernel.ld` 划定的。练习 1 已经验证了具体指令层面的地址计算，这里要回答另一个问题：链接脚本如何安排这些地址、为什么要这样安排。

`BASE_ADDRESS = 0x80200000` 加 `. = BASE_ADDRESS`，把整个内核的起始地址固定在这里。为什么必须是这个地址：OpenSBI 初始化完成后会跳转到 `0x80200000`，同时本项目的 QEMU 命令也用 `-device loader,...,addr=0x80200000` 把镜像放在这里，两者都固定了这个地址，所以内核的第一条指令必须位于此处。

需要说明的是，"内核必须加载到链接时假设的地址"这一结论对一般的地址相关代码成立：当指令中含有链接时算好的绝对地址时，加载位置变了这些地址就会失效。但就本项目而言，练习 1 中 `la sp, bootstacktop` 展开的 `auipc sp,0x3` 是 PC 相对寻址，其偏移 `0x3000` 只取决于 `kern_entry` 与 `bootstacktop` 的相对距离，并不依赖 `BASE_ADDRESS`；它在任何加载地址下都能算出正确的栈顶。因此，本内核固定在 `0x80200000` 的直接原因是 OpenSBI/QEMU 的约定，而不是这条指令。

**入口指令为什么落在 `0x80200000`：** 本组 `tools/kernel.ld` 中 `.text` 段的规则是 `*(.text.kern_entry .text .stub .text.* .gnu.linkonce.t.*)`，并没有指导书中单独的 `*(.text.kern_entry)` 一行；而 `entry.S` 使用的是普通 `.text` 段。所以 `kern_entry` 位于 `.text` 开头，并不是由某条"最前面"的匹配规则保证的，而是因为 `entry.o` 在链接输入中排在最前，其 `.text` 先被放入输出。另外，`ENTRY(kern_entry)` 只是在 ELF 头里记录入口符号；`objcopy -O binary` 得到的镜像没有头部，OpenSBI 并不读取入口信息，只是无条件跳到固定地址，所以真正起作用的是"第一条指令恰好是 `kern_entry`"这一布局事实。<!-- TODO(杨茜茹)：用 `head` 查看 obj/kernel.asm 的开头，确认 80200000 处确实是 kern_entry，并可顺便写出链接输入顺序。 -->

**逐行读脚本时注意到的一处细节**：`. = ALIGN(0x1000)` 只出现在 `.rodata` 和 `.data` 之间，`.text` 和 `.rodata` 之间没有，`.bss` 前面也没有单独对齐。直接可以确认的事实是：`.data` 从页边界开始，这与 `entry.S` 中 `.align PGSHIFT` 让 `bootstack` 页对齐是相互配合的（符号表中 `bootstack = 0x80201000`）。至于为什么只在这里对齐，我的一个**猜测**是为将来按页设置不同访问权限做准备（代码和只读数据与可读写数据分开）；但 lab1 还没有实现分页机制，这个猜测目前缺乏运行时证据支撑，只能算是读脚本结构得出的推测，留待后续涉及虚拟内存的实验去验证，不采信为既定事实。

链接脚本与 `init.c` 之间还有一处容易被忽略的直接耦合：`PROVIDE(edata = .)`、`PROVIDE(end = .)` 定义的符号，被 `kern_init` 直接用来计算 `.bss` 段范围并清零（`memset(edata, 0, end - edata)`）。这意味着链接脚本不只是给汇编代码看的"地图"，C 代码同样要靠它提供的符号才能正确初始化——如果有人改了链接脚本里段的排列顺序或漏掉某个 `PROVIDE`，最先暴露问题的很可能不是链接报错，而是运行时 `.bss` 没清零、全局变量里是垃圾值，这种故障远比链接失败更隐蔽、更难定位。

#### 小结

`kernel.ld` 不是一份静态的内存布局说明，它定义的地址约定和符号被 `entry.S`（建立栈）和 `init.c`（清零 `.bss`）两处代码分别、真实地消费着。这也是为什么修改链接脚本这类"看起来只是配置"的文件，必须对整条启动链路的影响有清楚认识，不能当成孤立参数去改。

### 功能模块：从 `cprintf` 到 SBI 控制台输出

**负责人：** 2413921-程子涵

#### 模块功能描述

本实验还没有可供内核调用的宿主操作系统标准库，因此格式化输出由实验代码自行实现。`kern/init/init.c` 中的 `kern_init` 调用 `cprintf`；`kern/libs/stdio.c` 中的 `cprintf` 和 `vcprintf` 把格式串及参数交给 `libs/printfmt.c` 的 `vprintfmt` 解析。每产生一个字符，回调 `cputch` 依次调用 `cons_putc`（`kern/driver/console.c`）和 `sbi_console_putchar`（`libs/sbi.c`）。最终 `sbi_call` 把功能号 `SBI_CONSOLE_PUTCHAR = 1` 放入 `a7/x17`，字符放入 `a0/x10`，执行 `ecall`，由 OpenSBI 提供控制台服务。链路可概括为：

```text
kern_init → cprintf → vcprintf → vprintfmt → cputch
          → cons_putc → sbi_console_putchar → sbi_call → ecall → OpenSBI 控制台
```

**核心函数的理解：**

- **`vprintfmt` 与回调设计。** `vprintfmt(putch, putdat, fmt, ap)` 只负责解析格式串（`%d`、`%s`、`%x`、宽度、`l` 修饰等），每产生一个字符就调用传入的函数指针 `putch(ch, putdat)`，自己并不知道字符最终去哪里。`vcprintf` 传入的是 `cputch` 和计数器地址 `&cnt`，于是格式化逻辑与输出设备解耦；同一个 `vprintfmt` 也被 `vsnprintf` 以 `sprintputch` 复用，把字符写入缓冲区。
- **`sbi_call` 的内联汇编。** C 语言无法直接发出 `ecall`，也无法指定变量放入哪个寄存器，所以用内联汇编完成：先把功能号和三个参数分别 `mv` 到 `x17`、`x10`、`x11`、`x12`，执行 `ecall` 陷入 M 态由 OpenSBI 处理，再把 `x10` 中的返回值取回 C 变量。输入/输出操作数（`"r"`/`"=r"`）让编译器把 C 变量放进某个寄存器，`"memory"` 约束告诉编译器这段汇编可能读写内存，避免优化时重排。
- **`cons_putc` / `cputch`。** `cons_putc` 只是对 `sbi_console_putchar` 的一层封装；`cputch` 在输出一个字符的同时累加计数，供 `cprintf` 返回已输出字符数。

这里的 `ecall` 是 S 模式内核向更高特权级固件请求服务；与以后用户程序向内核发起的系统调用使用同一类陷入机制，但请求方、服务方和调用约定不同。截图中的 `(THU.CST) os is loading ...` 是该链路产生的实际输出。

### 对操作系统的理解

#### 本实验知识点与 OS 原理的对应关系

**程子涵、杨茜茹：**

| 本实验中的知识点 | 对应的 OS 原理及关系、差异 |
|---|---|
| 从 `0x1000` 到 `0x80200000` 的启动交接 | 对应操作系统的引导过程。CPU 先执行复位引导代码，再进入固件，最后进入内核。实验用 QEMU 和 OpenSBI 展示了接力关系；真实机器还会有平台相关初始化、引导加载器和更多检查。 |
| 内核入口与独立启动栈 | 对应内核执行上下文和栈管理。`kern_entry` 设置 `sp` 后才进入 C 函数：进入内核时 `sp` 仍指向 OpenSBI 的栈，内核需要换成自己的栈。本实验只有一条简单执行路径，尚未涉及每个进程或每个 CPU 的内核栈。 |
| 链接脚本与内存布局（`.text`/`.rodata`/`.data`/`.bss`） | 对应程序的内存布局与链接。链接脚本决定各段的起始地址与排列，使内核镜像的第一条指令落在 `0x80200000`；`.bss` 在镜像中需要内核自己清零。差异：本实验直接使用物理地址，没有虚拟地址空间与页表。 |
| ELF 与 bin、`objcopy` | 对应可执行文件格式与加载。ELF 带段表与调试信息，由有操作系统的环境解析；bin 是按内存布局展开的线性镜像，适合固件直接加载。差异：本实验没有实现 ELF 加载器，加载由 QEMU 的 `-device loader` 完成。 |
| 地址相关代码与固定加载地址 | 对应程序的重定位与地址无关代码。含绝对地址的代码必须加载到链接时假设的位置；本内核固定在 `0x80200000`，原因是 OpenSBI/QEMU 的约定（`la` 使用的是 PC 相对寻址，本身不依赖加载地址）。 |
| `cprintf` 经 SBI 输出 | 对应分层 I/O 与硬件抽象。格式化层负责把数据转成字符，控制台层负责逐字符输出，SBI 层屏蔽底层设备差异。本实验借用固件服务，并没有实现完整的设备驱动、缓冲或文件描述符。 |
| S 模式执行 `ecall` | 对应特权级切换与陷入机制。内核通过 `ecall` 请求 M 模式 SBI 服务；原理课中的用户态系统调用通常是 U 模式陷入 S 模式。机制相似，但调用方向与服务对象不同。 |
| GDB 观察 PC、指令和寄存器 | 对应处理器状态与控制流分析。`pc` 表示下一条将要执行的指令地址，`sp` 表示当前栈顶；断点和单步让引导过程可验证。GDB 是实验调试手段，本身不是内核提供的运行时功能。 |

**原理课中重要、但 Lab 1 尚未实现的内容：**

1. **进程与线程调度：** 尚无进程控制块、上下文切换或调度算法；`kern_init` 输出后进入死循环。
2. **虚拟内存管理：** 尚无页表、地址空间隔离、缺页处理和页面置换；本实验主要观察链接与加载地址。
3. **中断和异常处理：** 虽通过 `ecall` 使用 SBI 服务，但没有实现完整的内核 trap 处理、外设中断分发及异常恢复。
4. **文件系统与持久化：** 控制台输出不等于文件 I/O，本实验没有目录、文件、缓存或磁盘管理。
5. **同步与并发：** 尚无锁、信号量及多任务竞争场景，也未讨论死锁处理。

#### 小组整体理解

这次实验让我们从一个最小可执行内核出发，把"一段 C 代码如何变成屏幕上的一行字"完整地走了一遍，也体会到：写一个裸机内核，意味着把平时在 Linux 上被工具链"默认"掉的环节——目标架构、链接脚本、标准库、加载地址——都显式地补回来。交叉编译对应原理课中"源代码如何变成目标平台可执行代码"（编译、汇编、链接）；用链接脚本把内核放在 `0x80200000` 对应"程序内存布局与地址相关性"；`make qemu` 的"编译 → 链接 → 镜像 → 加载"四步，则把抽象的构建系统与可执行文件格式（ELF 与 bin 的区别）落到了真实命令上。把整章串成"搭环境 → 定布局 → 走构建 → 走启动 → 造输出"一条链，我们才真正理解：操作系统之所以是"裸机之上的第一层软件"，正是因为它要亲手接过这些底层工作。

在入口点与内存布局上，印象最深的是汇编入口与链接脚本互相配合：`entry.S` 里的 `la sp, bootstacktop` 之所以能得到正确的栈顶，是因为链接脚本把内核放在 `0x80200000` 起的连续区域并确定了 `bootstack`/`bootstacktop` 的位置；而 `kern_init` 清零 `.bss` 靠的又是链接脚本 `PROVIDE(edata/end)` 导出的符号。固定在 `0x80200000` 是 OpenSBI 与 QEMU 的约定；栈向低地址增长是 ABI 约定，它决定了 `sp` 必须指向预留空间的顶端而非起点。

在启动流程与输出上，我们梳理了"复位引导代码（`0x1000`）→ 固件 OpenSBI（`0x80000000`）→ 内核入口（`0x80200000`）"的三级跳，以及内核借 `ecall` 请求 M 模式 SBI 服务、自底向上封装出 `cprintf` 的输出链路。据此，本实验知识点与 OS 原理可以这样对应：启动交接对应引导过程；内核入口与独立启动栈对应内核执行上下文与栈管理；`cprintf` 经 SBI 输出对应分层 I/O 与硬件抽象；S 模式 `ecall` 对应特权级切换与陷入机制（与用户态系统调用同类机制、但方向是 S→M 而非 U→S）；GDB 观察 PC/寄存器则对应处理器状态与控制流分析。反过来，原理课中重要的进程调度、虚拟内存、完整的中断异常处理、文件系统与同步并发，本实验都尚未触及——`kern_init` 输出后便进入死循环。

**杨茜茹（练习 1、内核入口点与内存布局）：** 我用 Claude 网页对话辅助阅读 `entry.S` 和链接脚本，并在 WSL/QEMU 环境搭建时用它协助排查权限与网络问题。我的做法是先自己通读源码，再带着具体问题提问；AI 讲解之后不直接采信，而是用 `obj/kernel.sym`、`obj/kernel.asm` 里的真实地址和反汇编核对。这次经验里最重要的教训来自答辩前的复核：AI 和课程文档都提到的 `*(.text.kern_entry)` 规则在本组实际的 `kernel.ld` 里并不存在，如果只对照文档就会写错。所以对 AI 的说法，必须回到自己的源码和编译产物上逐条确认，并把"验证过的结论"与"推理/推测"分开标注。

#### 程子涵的经验

**程子涵（练习 2、SBI 输出链路及知识点对比）：** 我把 AI 用于辅助阅读实验文档、核对术语和整理报告文字。我的主要工作是自己阅读 Makefile、入口汇编及输出链路源码，在 WSL 中启动 QEMU 和 GDB，逐条查看复位指令、记录 PC 与 `sp` 的变化，截取调试证据，并据此形成练习 2 的分析和与操作系统原理的对比。调试操作、现象记录和技术判断以我的工作为依据；AI 提供的文字仍需要我对照代码与截图复核。

这次调试让我认识到，提问时给出**明确的上下文、待解释的现象和回答边界**，比笼统询问"启动流程是什么"更有用。例如只设置 `0x80200000` 的写监视点后，GDB 一直显示 `Continuing.`；我依据断点与监视点的触发条件，重新启动并在同一地址设置执行断点，才观察到 `kern_entry`。AI 对概念的解释只能作为排查线索，不能替代 GDB 的寄存器值、反汇编和截图。对"是谁把镜像放到 `0x80200000`"这类容易概括过度的问题，还需要检查本项目 Makefile 的 `-device loader` 参数，区分 QEMU 加载镜像与 OpenSBI 交接控制权。

整理输出链路时，我先按源码画出 `cprintf → vprintfmt → cons_putc → sbi_console_putchar → ecall` 的调用路径，再借助 AI 检查自己对回调和 SBI 服务的理解。有效的协作方式是要求 AI 指明依据、列出不确定处，最后由我用源码和运行结果逐项验证。这样既提高了阅读效率，也保留了我对结论的独立判断。与本部分相应的任务式提示词见 [prompt.md](./prompt.md)；该文件是按工作内容整理的参考写法，不充当未经保存的历史对话记录。

#### 小组共同经验

三位成员都把 AI 定位为辅助阅读、提出核对线索，而把读源码、跑命令、记录现象、下结论的主体工作留在自己手上。共同的体会可以归结为两点：一是提问要给出明确的上下文与回答边界，比笼统地问"启动流程是什么"更有效——例如只设 `0x80200000` 写监视点后 GDB 一直 `Continuing.`，依据断点与监视点触发条件的区别改设执行断点，才观察到 `kern_entry`；二是 AI 的解释只能作为排查线索，不能替代编译产物、寄存器值、反汇编和截图，凡结论都要回到**本组自己的源码**和运行结果逐项验证，并区分"已证实的结论"与"推测"。
