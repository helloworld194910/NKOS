### 功能模块：内核入口点与内存布局

**负责人：** 2412790-杨茜茹

#### 模块功能描述

`entry.S` 里的指令能正确工作，前提是它们被安排在了正确的地址上——这件事不是 `entry.S` 自己决定的，而是 `tools/kernel.ld` 划定的。练习 1 已经验证了具体指令层面的地址计算，这里要回答另一个问题：链接脚本凭什么能保证这些地址是对的、安排成这样有什么道理。

`BASE_ADDRESS = 0x80200000` 加 `. = BASE_ADDRESS`，把整个内核的起始地址钉死在这里。我没有把这当成一个"约定俗成"就接受，而是去确认了这个约定不成立会怎样：C/汇编代码里对变量、函数的访存指令，在链接完成时就已经把具体地址写进了机器码编码本身——练习1 里验证过的 `auipc sp,0x3`，这个 `0x3` 就是根据 `BASE_ADDRESS` 在编译期算死的。如果实际加载地址和这个约定不一致，这类写死的地址全部失效，代码从第一条指令起就是错的，这不是"可能出问题"，而是必然出问题。`ENTRY(kern_entry)` 加上排在 `.text` 段最前面的 `*(.text.kern_entry)` 匹配规则，两者合起来保证了 OpenSBI 跳到 `0x80200000` 时，落地的第一条指令必须是 `kern_entry`，不存在"大概率是"这种模糊地带。

**逐行读脚本时注意到的一处细节**：`. = ALIGN(0x1000)` 只出现在 `.rodata` 和 `.data` 之间，`.text` 和 `.rodata` 之间没有，`.bss` 前面也没有单独对齐。我的判断是，这不是随手安排的——`.text`（代码）和 `.rodata`（只读常量）都不需要写权限，可以共享同一批内存页；但 `.data`（可读写全局变量）一旦将来引入内存保护机制，就必须从页边界开始独占空间，否则没法只对这一页开放写权限。`.bss` 紧跟 `.data` 且不再单独对齐，同样符合"可读写内容划进同一组权限管理"这个逻辑。但我没有把这个判断写成确定结论——lab1 本身还没有实现分页机制，这个推测目前缺乏运行时证据支撑，只能算是读脚本结构得出的合理猜测，留待后续涉及虚拟内存的实验去验证，不采信为既定事实。

链接脚本与 `init.c` 之间还有一处容易被忽略的直接耦合：`PROVIDE(edata = .)`、`PROVIDE(end = .)` 定义的符号，被 `kern_init` 直接用来计算 `.bss` 段范围并清零。这意味着链接脚本不只是给汇编代码看的"地图"，C 代码同样要靠它提供的符号才能正确初始化——如果有人改了链接脚本里段的排列顺序或漏掉某个 `PROVIDE`，最先暴露问题的很可能不是链接报错，而是运行时 `.bss` 没清零、全局变量里是垃圾值，这种故障远比链接失败更隐蔽、更难定位。

#### 小结

`kernel.ld` 不是一份静态的内存布局说明，它定义的地址约定和符号被 `entry.S`（建立栈）和 `init.c`（清零 `.bss`）两处代码分别、真实地消费着。这也是为什么修改链接脚本这类"看起来只是配置"的文件，必须对整条启动链路的影响有清楚认识，不能当成孤立参数去改。

### 功能模块：从 `cprintf` 到 SBI 控制台输出

**负责人：** 2413921-程子涵

#### 模块功能描述

本实验还没有可供内核调用的宿主操作系统标准库，因此格式化输出由实验代码自行实现。`kern/init/init.c` 中的 `kern_init` 调用 `cprintf`；`kern/libs/stdio.c` 中的 `cprintf` 和 `vcprintf` 把格式串及参数交给 `libs/printfmt.c` 的 `vprintfmt` 解析。每产生一个字符，回调 `cputch` 依次调用 `cons_putc`（`kern/driver/console.c`）和 `sbi_console_putchar`（`libs/sbi.c`）。最终 `sbi_call` 把功能号 `SBI_CONSOLE_PUTCHAR = 1` 放入 `a7/x17`，字符放入 `a0/x10`，执行 `ecall`，由 OpenSBI 提供控制台服务。链路可概括为：

```text
kern_init → cprintf → vcprintf → vprintfmt → cputch
          → cons_putc → sbi_console_putchar → sbi_call → ecall → OpenSBI 控制台
```

这里的 `ecall` 是 S 模式内核向更高特权级固件请求服务；与以后用户程序向内核发起的系统调用使用同一类陷入机制，但请求方、服务方和调用约定不同。截图中的 `(THU.CST) os is loading ...` 是该链路产生的实际输出。

我先沿 `kern_init` 的调用点逐层查找函数定义，自己整理上述输出链路，再用 AI 辅助解释 `vprintfmt` 的字符回调和 SBI 寄存器约定。对 AI 给出的说法，我回到 `kern/libs/stdio.c`、`kern/driver/console.c` 和 `libs/sbi.c` 核对调用关系与寄存器赋值，并用启动输出截图确认实际现象。本部分没有让 AI 生成或修改内核代码，也没有进行“生成代码后多轮修复”的迭代；对应的阅读辅助提示词整理在 [prompt.md](./prompt.md) 中。

### 练习 1：理解内核启动中的程序入口操作

**负责人：** 2412790-杨茜茹

**问题：** 阅读 `kern/init/entry.S` 内容代码，结合操作系统内核启动流程，说明指令 `la sp, bootstacktop` 完成了什么操作，目的是什么？`tail kern_init` 完成了什么操作，目的是什么？

**分析：**

OpenSBI 把控制权交到 `0x80200000` 时，除了 PC 指向这里，没有为接下来的代码准备任何执行环境，尤其没有栈。而紧接着要执行的 `kern_init` 是 C 函数，任何一次函数调用都要用到栈。`entry.S` 只有两条真正执行的指令，拆开看，这两条指令恰好分别对应"搭建执行环境"和"移交控制权"这两件必须做、且只能做一次的事。

**`la sp, bootstacktop`：** 这是一条伪指令，表面上看是"把地址装进寄存器"，但我没有停留在这个字面解释上，而是去查了它展开后的真实指令（`obj/kernel.asm`）：

80200000: auipc sp,0x3
80200004: mv sp,sp


确实被拆成了两条。这里我排除了"随便哪种方式都行"这种想法——RISC-V 指令编码定长 32 位，一条指令根本装不下一个完整的目标地址，所以必须靠 `auipc`（以当前 PC 为基准、加一个高位偏移）先拼出一个大致地址，这不是编译器"多此一举"，而是指令集本身的硬性限制决定的。我用符号表（`obj/kernel.sym`）核对了这个偏移量算出来的结果：`bootstack = 0x80201000`，`bootstacktop = 0x80203000`，`0x80200000 + 0x3000` 正好等于 `0x80203000`，验证了这条"PC 相对寻址"确实精确落在目标地址上，不是凑巧。

栈指针设在 `bootstacktop`（区间顶端）而不是 `bootstack`（起点），我一开始以为是随意的命名习惯，后来确认这是和 RISC-V 栈"从高地址向低地址增长"这个架构约定强绑定的——如果设在起点，第一次压栈就会立刻写出预留空间之外，这不是风格问题，是会直接导致错误的设计约束。这块空间大小是 `KSTACKPAGE(2) × PGSIZE(4096) = 8192` 字节，符号表里 `0x80203000 - 0x80201000 = 0x2000` 也印证了这一点。至于为什么具体选了 2 页而不是 1 页或更多，`entry.S` 和 `memlayout.h` 本身没有给出直接依据，我没有采信"随便取个经验值"这类缺乏支撑的说法，这里如实标注为待后续实验验证的开放问题，而不是强行给出一个解释。

**`tail kern_init`：** 跳转到 `kern_init`，且不保存返回地址。我验证了一个假设：如果把这条指令换成普通的 `call kern_init`，单从运行结果看，会不会出错？结论是不会——因为 `kern_init` 本身进入死循环、永不返回，`ra` 寄存器里存不存东西根本不会被用到。但这恰恰说明 `tail` 的价值不在于"不用就会错"，而在于它用指令本身准确表达了"这是终点，不是中转站"这个设计意图，同时省掉了一次多余的寄存器写入。这个判断和 `kern_init` 在 `init.c` 中被标注 `__attribute__((noreturn))` 是互相印证的——一处用汇编指令的选择、一处用 C 语言的函数属性，各自独立地表达了同一个事实。

**问题回答：** `la sp, bootstacktop` 通过 `auipc` 与偏移拼接出预留栈空间顶端的地址（`0x80203000`）并装入 `sp`，目的是在进入 C 代码前建立可用的函数调用环境，这一实现方式本身是 RISC-V 定长指令编码限制下的必然结果，不是设计者的任意选择。`tail kern_init` 以不保存返回地址的方式跳转到 `kern_init`，目的是把控制权永久移交给内核初始化逻辑；经过对比验证，换成普通调用不会导致功能错误，但 `tail` 更准确地表达了"内核启动是单向流程"这一设计意图，这是语义层面而非正确性层面的选择。

### 练习 2：使用 GDB 验证启动流程

**负责人：** 2413921-程子涵

**问题：** RISC-V 硬件加电后最初执行的几条指令位于什么地址？它们主要完成哪些功能？

**调试过程与观察：**

1. 在 WSL 的实验目录执行 `make debug`。本项目的 Makefile 用 `-s -S` 启动 QEMU：开放本地 GDB 端口并让虚拟 CPU 在启动时暂停。另一终端执行 `make gdb`，加载 `bin/kernel` 的调试符号，按 RV64 架构连接 `localhost:1234`。连接后 GDB 显示当前 PC 为 `0x1000`。

4. 重新从起点对 `0x80200000` 设置执行断点并继续运行。GDB 在 `kern_entry` 的 `kern/init/entry.S:7` 停下，`p/x $pc` 显示 `0x80200000`。此时反汇编显示先设置 `sp`，随后跳转到 `kern_init`。进一步单步后 `sp` 从进入内核时的 `0x8001bd80` 变为 `0x80203000`，证实内核切换到自己的启动栈。

## 六、实验总结与收获

### 对操作系统的理解

**程子涵：本实验知识点与 OS 原理的对应关系**

| 本实验中的知识点 | 对应的 OS 原理及关系、差异 |
|---|---|
| 从 `0x1000` 到 `0x80200000` 的启动交接 | 对应操作系统的引导过程。CPU 先执行复位引导代码，再进入固件，最后进入内核。实验用 QEMU 和 OpenSBI 展示了接力关系；真实机器还会有平台相关初始化、引导加载器和更多检查。 |
| 内核入口与独立启动栈 | 对应内核执行上下文和栈管理。`kern_entry` 设置 `sp` 后才进入 C 函数，说明内核运行不能继续依赖固件先前的栈。本实验只有一条简单执行路径，尚未涉及每个进程或每个 CPU 的内核栈。 |
| `cprintf` 经 SBI 输出 | 对应分层 I/O 与硬件抽象。格式化层负责把数据转成字符，控制台层负责逐字符输出，SBI 层屏蔽底层设备差异。本实验借用固件服务，并没有实现完整的设备驱动、缓冲或文件描述符。 |
| S 模式执行 `ecall` | 对应特权级切换与陷入机制。内核通过 `ecall` 请求 M 模式 SBI 服务；原理课中的用户态系统调用通常是 U 模式陷入 S 模式。机制相似，但调用方向与服务对象不同。 |
| GDB 观察 PC、指令和寄存器 | 对应处理器状态与控制流分析。`pc` 表示下一条指令地址，`sp` 表示当前栈顶；断点和单步让引导过程可验证。GDB 是实验调试手段，本身不是内核提供的运行时功能。 |

**原理课中重要、但 Lab 1 尚未实现的内容：**

1. **进程与线程调度：** 尚无进程控制块、上下文切换或调度算法；`kern_init` 输出后进入死循环。
2. **虚拟内存管理：** 尚无页表、地址空间隔离、缺页处理和页面置换；本实验主要观察链接与加载地址。
3. **中断和异常处理：** 虽通过 `ecall` 使用 SBI 服务，但没有实现完整的内核 trap 处理、外设中断分发及异常恢复。
4. **文件系统与持久化：** 控制台输出不等于文件 I/O，本实验没有目录、文件、缓存或磁盘管理。
5. **同步与并发：** 尚无锁、信号量及多任务竞争场景，也未讨论死锁处理。

### AI 协作开发的经验

**程子涵（练习 2、SBI 输出链路及知识点对比）：** 我把 AI 用于辅助阅读实验文档、核对术语和整理报告文字。我的主要工作是自己阅读 Makefile、入口汇编及输出链路源码，在 WSL 中启动 QEMU 和 GDB，逐条查看复位指令、记录 PC 与 `sp` 的变化，截取调试证据，并据此形成练习 2 的分析和与操作系统原理的对比。调试操作、现象记录和技术判断以我的工作为依据；AI 提供的文字仍需要我对照代码与截图复核。

这次调试让我认识到，提问时给出**明确的上下文、待解释的现象和回答边界**，比笼统询问“启动流程是什么”更有用。例如只设置 `0x80200000` 的写监视点后，GDB 一直显示 `Continuing.`；我依据断点与监视点的触发条件，重新启动并在同一地址设置执行断点，才观察到 `kern_entry`。AI 对概念的解释只能作为排查线索，不能替代 GDB 的寄存器值、反汇编和截图。对“是谁把镜像放到 `0x80200000`”这类容易概括过度的问题，还需要检查本项目 Makefile 的 `-device loader` 参数，区分 QEMU 加载镜像与 OpenSBI 交接控制权。

整理输出链路时，我先按源码画出 `cprintf → vprintfmt → cons_putc → sbi_console_putchar → ecall` 的调用路径，再借助 AI 检查自己对回调和 SBI 服务的理解。有效的协作方式是要求 AI 指明依据、列出不确定处，最后由我用源码和运行结果逐项验证。这样既提高了阅读效率，也保留了我对结论的独立判断。与本部分相应的任务式提示词见 [prompt.md](./prompt.md)；该文件是按工作内容整理的参考写法，不充当未经保存的历史对话记录。
